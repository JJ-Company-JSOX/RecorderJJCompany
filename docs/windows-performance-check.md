# Windows 检查与性能记录（2026-10-17）

## 范围与文件保护

检查机器为 Intel Core Ultra 7 155U（12 核 / 14 线程）、约 16 GiB RAM、Intel Graphics，检查时系统剩余 RAM 约 3.7 GiB，C 盘可用约 280 GiB。工作使用独立的 `jsox-preview` Git checkout；下载目录的源码副本保留，Canvid 安装文件保持只读。该机原 `Recordly-dev/recordings` 下只有空 Projects 目录，因此没有使用旧电脑的录像。

诊断素材全部为合成视频/光标样本；测试进程使用 `RECORDLY_DIAGNOSTICS_USER_DATA` 隔离配置、项目和缓存。原始报告、日志、截图和视频在 Git 忽略的 `.tmp/`，不上传。未调用付费 API、下载 AI 模型或部署云服务。

## 已实施

- Windows 窗口几何查询改 UTF-16LE EncodedCommand，并隐藏 PowerShell 控制台；查询失败时保留全屏选择。此机原查询本来成功，不能宣称复现或加速了旧机故障。
- 视频会话批准列表保留同名、存在且真实路径相符的 mic/system 音轨，支持 `.m4a`；不开放整个父目录。缺失音轨与访问拒绝分别处理。音轨探测不能自行批准任意视频。
- 编辑器播放器、悬停预览、缩略图渲染器、AutoEdit 和导出器按需加载。移除图标库根导入；图标源码属于构建依赖，不再作为运行时依赖随包重复收集。
- 均衡预览按 CSS 尺寸渲染、最长边最高 1280 像素；可切回完整显示密度。仅限制合成画布，不改变源文件、项目数据、导出尺寸或导出画质；本轮未实现解码代理视频。
- 暂停后停止 Pixi ticker，编辑、定位和播放时唤醒。live ref getters 防止调用者拿到初始化前的空播放器引用；视频卸载时先移除旧 sprite，再释放 GPU source。
- 修复重复导入当前视频、重开同源项目时的元数据刷新。Vite 不再监视 `.tmp`、测试包和 native build 目录，避免诊断 profile 的锁定 Cookies 数据库导致 EBUSY。
- 本机实测 Electron 43.1 / Chromium 150 的编辑器 `webSecurity:false` 导致 VideoEncoder/VideoDecoder 均不可用；同页面 `webSecurity:true` 时恢复。编辑器改为开启，媒体使用已有 allowlist + CORS loopback server；未放宽文件访问策略。
- 增加 `build:win:test` / `package:win:test`，本地测试包禁发布、禁自动更新、跳过现场 native 编译，复用本机 Electron 和经过哈希校验的 helpers。普通发布目标改为用户 fork；保留上游作者/许可证归属。

## 性能证据与限制

相同合成 1920×1080 / 60fps / 8 秒 H.264 + AAC 素材，实际桌面 DPR 1.5。每轮播放采样约 4 秒，独立诊断 profile。以下为初始基线两轮和首轮优化后的观测，后者仍有构建等背景活动；不是严格控制环境的统计结论。原始数据见 `.tmp/before-1080/`、`.tmp/before-1080-repeat/`、`.tmp/after-1080/`。

| 项目 | 初始两轮 | 首轮优化后 |
|---|---:|---:|
| 预览就绪 | 10.24 / 13.68 秒 | 11.68 秒 |
| 画布像素（相同 CSS 617×347） | 926×521 | 617×347（减少约 55.6%） |
| 视频掉帧 / 总帧 | 181/251、176/243 | 161/243 |
| RAF 回调间隔 p95 | 114.8 / 153.3 ms | 72.6 ms |
| GPU 进程工作集 | 840 / 812 MiB | 761 MiB |
| 各进程工作集相加 | 1512 / 1482 MiB | 1581 MiB |

工作集相加包含共享页面，不能等同物理 RAM。此轮未证明整体 RAM 或预览启动耗时改善；掉帧仍然明显。直接播放相同原视频也分别掉帧 55/236、72/238，说明环境/解码也存在负担，编辑器合成进一步加重。不能把打包成功、静态模块减少或这些小样本等同流畅度问题全部解决。

完整修复后的追加一轮（`.tmp/verified-1080/`，没有并行构建/回归）：窗口 0.45 秒、预览 3.27 秒；掉帧 94/243（38.7%），RAF p95 33.5ms，GPU 工作集约 551 MiB，各进程工作集相加约 1439 MiB；直接播放原视频为 0/240 掉帧。缓存和其他应用负载与最初不同，不能把全部差异归因于代码。该轮明确显示编辑器仍比原始播放更吃力，未达到 60fps，RAM 整体改善有限。

静态入口可达本地模块 309 → 251；生产构建转换模块 8174 → 3659，EditorWindow 主块约 1.46 MB → 0.85 MB。原构建约 178 秒，后续为 67–81 秒，但缓存/系统负载不同，仅作构建开销记录。

## Windows 录制与声音

`scripts/smoke-windows-capture.mjs` 只录置顶合成窗口，真实麦克风关闭。首轮请求 60fps，303 帧 / 7.10 秒 ≈ 42.68fps，未通过 60fps；与 UI 回归并行且生成器有额外开销，不能作为硬件上限。后续请求 30fps，177 帧 / 6.40 秒 ≈ 27.66fps，实际 cadence 达到脚本 90% 阈值，但名义帧率仍报告 60，整轮断言仍未全通过。

两轮均输出合成区域尺寸及色块匹配的视频，并录到非静音系统音轨和 997 Hz 合成测试音。首轮有 112 次 discontinuity、17 次 gap fill，音画延迟需继续检查；不能由“有音轨”判定音质、同步或真实麦克风全部通过。

WGC/CUDA helper 二进制哈希符合随附 manifest，但源码 fingerprint 陈旧。本轮没有声称验证当前 native 源码重建，或已解决原生捕获帧率/音频连续性。

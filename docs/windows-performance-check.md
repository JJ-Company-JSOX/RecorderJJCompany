# Windows 检查与性能记录（2026-10-17）

## 范围与文件保护

检查机器为 Intel Core Ultra 7 155U（12 核 / 14 线程）、约 16 GiB RAM、Intel Graphics，检查时系统剩余 RAM 约 3.7 GiB，C 盘可用约 280 GiB。工作使用独立的 `jsox-preview` Git checkout；下载目录的源码副本保留，Canvid 安装文件保持只读。该机原 `Recordly-dev/recordings` 下只有空 Projects 目录，因此没有使用旧电脑的录像。

## 已实施

- Windows 窗口几何查询改 UTF-16LE EncodedCommand，并隐藏 PowerShell 控制台；查询失败时保留全屏选择。此机原查询本来成功，不能宣称复现或加速了旧机故障。
- 视频会话批准列表保留同名、存在且真实路径相符的 mic/system 音轨，支持 `.m4a`；不开放整个父目录。缺失音轨与访问拒绝分别处理。音轨探测不能自行批准任意视频。
- 编辑器播放器、悬停预览、缩略图渲染器、AutoEdit 和导出器按需加载。移除图标库根导入；图标源码属于构建依赖，不再作为运行时依赖随包重复收集。
- 均衡预览按 CSS 尺寸渲染、最长边最高 1280 像素；可切回完整显示密度。仅限制合成画布，不改变源文件、项目数据、导出尺寸或导出画质；本轮未实现解码代理视频。
- 暂停后停止 Pixi ticker，编辑、定位和播放时唤醒。live ref getters 防止调用者拿到初始化前的空播放器引用；视频卸载时先移除旧 sprite，再释放 GPU source。
- 修复重复导入当前视频、重开同源项目时的元数据刷新。Vite 不再监视 `.tmp`、测试包和 native build 目录，避免诊断 profile 的锁定 Cookies 数据库导致 EBUSY。
- 本机实测 Electron 43.1 / Chromium 150 的编辑器 `webSecurity:false` 导致 VideoEncoder/VideoDecoder 均不可用；同页面 `webSecurity:true` 时恢复。编辑器改为开启，媒体使用已有 allowlist + CORS loopback server；未放宽文件访问策略。
- 增加 `build:win:test` / `package:win:test`，本地测试包禁发布、禁自动更新、跳过现场 native 编译，复用本机 Electron 和经过哈希校验的 helpers。普通发布目标改为用户 fork；保留上游作者/许可证归属。

### 第二轮：播放时无关界面更新

CPU profile 显示 React 控件的 props 合并、hooks 与提交占用明显。播放时 `onTimeUpdate` 每 RAF 更新编辑器根状态，设置面板也重复构建。现在 `SettingsPanel` 使用默认浅比较 memo，稳定 zoom/音频恢复等回调；只有正在显示的字幕编辑/摄像头裁切面板接收播放时钟。主视频、鼠标、音频和时间线仍使用原精度时间，未通过降低播放时钟频率换取数字改善。transport 缓存排序后的片段和时长，替换数组或显式 refresh 时更新；字幕时间线回调保持稳定。

回归还发现播放器在只有视频元数据时就通知“就绪”，冷启动下 Pixi/transport 尚未建立，立即点 Play 可能没有响应。就绪通知现移到 transport 初始化之后，并同时要求 Pixi、视频和 transport 可用。测试中同时纠正了 60 秒 readiness 断言被 30 秒总预算提前终止，以及 HUD 尚在初始化时使用默认 5 秒等待的问题；这些测试等待不作为生产启动耗时。

离线包整体验证还实际遇到 `EPERM`：原子 rename 替换项目失败，磁盘仍保留旧的光标关闭状态，尽管界面已开启。原子写入现对 Windows 的 EPERM/EACCES/EBUSY 在 rename 阶段有界退避重试（每处至多约 1.6 秒等待），项目和备份两处都适用；仍保持临时文件同步、备份上一代、按项目串行写入，绝不删除目标文件来强行替换。永久锁或其他错误会保留原文件并返回失败。若主项目已缺失，唯一恢复备份现在保留到新目标成功同步之后才清理；清理失败保留备份并警告，不误报已提交的项目保存失败。单元回归覆盖临时目标锁、备份锁、耗尽重试、非锁错误立即失败、原文件/备份完整、唯一恢复备份保留、排队中的下一次写入及后续保存恢复。

## Windows 录制与声音

`scripts/smoke-windows-capture.mjs` 只录置顶合成窗口，真实麦克风关闭。首轮请求 60fps，303 帧 / 7.099767 秒 ≈ 42.68fps，P95 帧间隔 33.334ms，未达到请求 cadence；与 UI 回归并行且生成器有额外开销，不能作为硬件上限。后续请求 30fps，177 帧 / 6.3998 秒 ≈ 27.66fps，P95 帧间隔 50ms，达到脚本 90% cadence 阈值。这些是解码后的视频样本数，可能包括 helper 补出的重复帧，不能等同独立捕获画面的更新率。

原报告把 FFprobe `r_frame_rate` 标成 `nominalFps` 并单独与请求值比较：两轮该字段都是 `60/1`，所以 30fps 整轮因这项旧断言失败。它不能单独证明 fps 参数未生效；30fps 文件的 `avg_frame_rate=885000/31999`、`time_base=1/30000`、`codec_time_base=1/60`，与 60fps 文件的对应字段也有区别。当前源码明确把 `config.fps` 传给编码器输入和输出媒体类型，但这些旧二进制结果尚不能验证当前源码。脚本版本 2 保留原始比率、时间基及解码帧时间戳统计，结合平均帧率、时间基有效性和请求值 ±10% 的实测 cadence 判断；不再用 `r_frame_rate` 的单一相等性判定。两个历史样本均呈现可变时间戳间隔，应作为 VFR 观测解读；提高容器样本数或补重复帧也不代表捕获变流畅。旧报告保持原样，不把脚本修正视为重测通过。

两轮均输出合成区域尺寸相符的视频；首轮色块验证失败，30fps 轮通过。两轮均录到非静音系统音轨和 997 Hz 合成测试音。首轮有 112 次 discontinuity、17 次 gap fill，30fps 轮分别为 9 和 1，连续性仍需检查；不能由“有音轨”判定音质、同步或真实麦克风全部通过。

WASAPI 元数据的 `startDelayMs` 表示音轨首个可靠数据包相对首个视频帧的起始 offset，并非直接测得设备启动延迟或丢失音频。测试刻意在观察到 `Recording started` 后才创建 AudioContext、启动测试音：首轮 offset 2126ms、WAV 约 5005ms，30fps 轮 offset 999ms、WAV 约 5402ms；后者相加约 6401ms，与视频约 6399.8ms 接近。因此“WAV 比视频短约一秒”本身不能证明丢失了一秒声音。版本 2 记录 helper 启动后的开始信号、测试音请求/返回时间，以及渲染器时钟下振荡器的调度时间和 AudioContext latency 字段；两种时钟原点不同，调度时间也不能等同扬声器实际发声时间。辅助 mux 继续应用元数据 offset，不据此宣布音画同步已验证。

WGC/CUDA helper 二进制哈希符合随附 manifest，但源码 fingerprint 陈旧。本轮没有声称验证当前 native 源码重建，或已解决原生捕获帧率/音频连续性。只读检查显示当前 WGC 源码在到帧回调内同步进行 GPU→CPU Map、标量 BGRA→NV12 转换、缓存复制及 SinkWriter 写入，可能造成回调阻塞；这是源码上的排查方向，尚未证明旧 helper 的具体瓶颈。本机 PATH 和常见安装位置未发现 CMake、MSVC/Visual Studio、LLVM 或 Windows SDK；当前可交付的是已有二进制，不能把未编译的 native 源码调整写成已生效。

第二轮无并行构建/回归的真实 helper 重测：60fps 请求为 362 帧 / 6.283117 秒 ≈ 57.61fps，P95 16.667ms；30fps 请求为 181 帧 / 6.2498 秒 ≈ 28.96fps，P95 50ms。合成窗口自身更新率分别约 58.87、58.49fps，新增检查防止把慢生成器误判为捕获瓶颈。两轮尺寸、三处色块、正向时间戳、平均帧率和 ±10% cadence、非静音 997Hz 系统音及辅助 mux 检查均通过，报告在 `.tmp/capture-smoke/2026-10-17T05-39-18-053Z/` 与 `2026-10-17T05-39-30-994Z/`。这是同一个旧 helper 的隔离复测，并非 native 代码优化结果；两个文件仍是 VFR，分别有 5、16 次音频 discontinuity，不能宣称音质/音画同步已全部验证。真实麦克风仍未采样。

# Distribution license review

Reviewed 2026-10-19 against this checkout and actual Windows binaries. This is an engineering compliance inventory, not legal clearance.

## Current blockers to a closed-source release

The repository's `LICENSE.md` is AGPL-3.0. Adding MIT/Apache AI components does not make the existing Recordly application permissively licensed. Preserve its copyright/license and satisfy applicable corresponding-source and network-use obligations. A closed-source product requires permission from all relevant rights holders or a properly separated independently implemented alternative reviewed for that purpose. Changing package branding or repository URL does not resolve this.

The installed `ffmpeg-static` package supplies `ffmpeg version 6.1.1-essentials_build-www.gyan.dev`, with `--enable-gpl --enable-version3 --enable-libx264 --enable-libx265`. Do not describe this executable as an LGPL-only build. [FFmpeg's official legal guidance](https://ffmpeg.org/legal.html) explains build-dependent obligations. Before external commercial distribution, provide the exact binary's matching complete source/build materials and required licenses/notices; a generic current FFmpeg Git URL is insufficient. Codec patent/licensing questions depend on markets and distribution/use, independently of open-source copyright licenses. Rebuilding an audited LGPL-compatible configuration and using permitted encoding paths is a possible future option, not a completed compliance fix.

The offline AI edition's narration voice ships eSpeak NG (GPL-3.0-or-later) in two forms. The first is the eSpeak NG library itself, with its ucd-tools, compiled statically into sherpa-onnx 1.13.8's native library `sherpa-onnx-c-api.dll`. That DLL ships in every Windows package, in `node_modules/sherpa-onnx-win-x64` (`sherpa-onnx-node` is a regular dependency and `electron-builder.json5` unpacks it from the asar), and, as the same file (SHA-256 `b0801cd8eeead83213c60b92cc004de6f3ac4cd4a9ac7c388c16b97c590f1e99`), in the shared runtime `offline-tools/sherpa/runtime` of the offline AI and tools editions. sherpa-onnx v1.13.8 builds it from csukuangfj/espeak-ng `ed530aa` (`cmake/espeak-ng-for-piper.cmake`) together with piper-phonemize (MIT, csukuangfj/piper-phonemize `f3ff95a`, `cmake/piper-phonemize.cmake`). Checked 2026-10-22: the Windows DLL from `sherpa-onnx-win-x64@1.13.8` contains eSpeak NG's messages ("Use espeak-ng to handle the OOV", "Failed to initialize espeak-ng with data dir") and piper's `phonemize_eSpeak`, and the Linux build of the same version has eSpeak NG's internals (`TranslateWord`, `LoadVoice`, `SetUpPhonemeTable`), ucd-tools' `ucd_lookup_category` and `piper::phonemize_eSpeak` linked in, with no eSpeak NG shared library among its dependencies. The npm package says only "Apache-2.0" and ships no license file. Kokoro uses this code for every non-Chinese word it says. The second form is the data (`resources/offline-ai/tts-kokoro/espeak-ng-data`), partly in object form: 118 of its 355 files are compiled (113 `*_dict` dictionaries plus `phondata`, `phondata-manifest`, `phonindex`, `phontab` and `intonations`); their preferred form for modification is eSpeak NG's `dictsource/` and `phsource/`. The voice's MODEL-LICENSE.txt and NOTICE only link to a third-party fork revision this project does not control ([csukuangfj/espeak-ng `ed530aa`](https://github.com/csukuangfj/espeak-ng/tree/ed530aa113046142eb5115cf2fc9157854d0ffe1)), and no source archive or offer ships with the package. Checked 2026-10-22 by building that revision on Linux with its CMake build: 343 of the 355 shipped files are byte-identical to the build (all 237 text files and 106 of the compiled ones); the other 12 dictionaries (as, bn, chr, da, ja, ko, kok, my, sd, shn, th, vi) have the same size and the same bytes, ordered differently inside their rules section, so that revision is very likely, but not proven, to be their source. Before external distribution: (1) publish a source archive of that exact revision under this project's control (for example `git archive` of `ed530aa`, next to each installer download with its SHA-256, kept available as long as GPL-3.0 section 6(d) requires) and name its location in the voice's NOTICE and in `THIRD_PARTY_NOTICES.md`, or ship it inside the package; (2) close the 12-file gap, either by confirming those files come from that revision or by building `espeak-ng-data` from the pinned source on the build machine and pinning that output in `scripts/offline-tts.lock.json`; (3) cover the DLL as well: for object code that has eSpeak NG linked in, GPL-3.0's corresponding source is the source of the whole library, so the archive must also hold sherpa-onnx v1.13.8 itself, every dependency archive its `cmake/` files pin (eSpeak NG `ed530aa`, piper-phonemize `f3ff95a`, OpenFst, kaldi-native-fbank, kaldi-decoder, simple-sentencepiece, nlohmann/json, hclust-cpp and the rest) and the build scripts. The DLL is a third-party prebuilt, so either confirm the sherpa-onnx release workflow that built it and archive exactly those inputs, or build the DLL from that source on the build machine and pin the result. Like the FFmpeg item above, this applies to every Windows package that carries the DLL, not only the offline AI edition, although only Kokoro makes the eSpeak NG code do work; (4) the tools edition's shared runtime folder (written by `scripts/prepare-offline-sherpa.mjs`) still calls the DLL Apache-2.0 in its NOTICE and ships neither the GPL-3.0 nor the piper-phonemize MIT text: add both there before that edition is released. The offline AI edition carries both texts in the voice's MODEL-LICENSE.txt.

The Kokoro-82M v1.0 voice is the default narration voice of the offline AI edition, and its training-data review is incomplete. The authoritative model card (`hexgrad/Kokoro-82M` on Hugging Face) could not be opened from the review machine. A third-party GitHub copy of the v1.0 card and the author's README (see `MODEL_LICENSES.md`) say it was trained only on public-domain audio, Apache/MIT-licensed audio, CC BY audio (Koniwa tnc, CC BY 3.0; SIWIS, CC BY 4.0) and synthetic audio generated by closed TTS models from large providers. That does not change the Apache-2.0 grant for the weights, but whether producing the synthetic audio was allowed by those providers' terms is a provenance risk this project cannot check. This is a commercial-release blocker until (a) someone reads the card at a pinned Hugging Face revision from a machine that can reach it and records the revision and its training-data text here, and (b) the release owner accepts the synthetic-audio and CC BY attribution position in writing. If it is not cleared, ship the older voices instead: run `npm run prepare:offline-tts -- --legacy-vits`, package `tts/**` and `tts-en/**` instead of `tts-kokoro/**` in `electron-builder.offline.json5`, and point the packaging checks (`verify:offline-tts`, `smoke:packaged-binaries`) at those folders. The app uses those voices on its own when Kokoro is absent (no voice choice, and Chinese lines keep the `设置（Settings）` style).

## Current AI distribution inventory

- `scripts/offline-ai.lock.json`, `scripts/offline-ai-build.lock.json`: pinned Qwen/llama artifacts and portable compiler. Full model/runtime licenses accompany `resources/offline-ai`.
- `scripts/offline-speech.lock.json`: OpenAI Whisper multilingual small Q5_1, immutable conversion revision and SHA; MIT model notice separately from whisper.cpp code.
- `scripts/build-offline-whisper-runtime.mjs`: pinned whisper.cpp source, static Windows CPU build, bundled MIT/toolchain/embedded component notices. No copied proprietary Canvid implementation.
- `scripts/offline-tts.lock.json`: Kokoro-82M v1.0 narration voice (sherpa-onnx fp32 conversion, weights Apache-2.0), its lexicons (misaki data, Apache-2.0; pypinyin data, MIT), the icefall text-normalization FSTs (Apache-2.0) and eSpeak NG's `espeak-ng-data` (GPL-3.0-or-later, see the source obligation above), every one of the 363 files pinned by size and SHA-256 against the pinned release archive; `resources/offline-ai/tts-kokoro` carries MODEL-LICENSE.txt (the Apache-2.0, MIT and GPL-3.0 texts and piper-phonemize's MIT text, each pinned by commit and SHA), NOTICE (which also names the eSpeak NG and piper-phonemize code compiled into the sherpa-onnx engine, from the lock's `engineStaticLibraries`) and the manifest. The older VITS voices in the same lock are not packaged.
- `scripts/offline-ocr.lock.json`: PP-OCRv6 small detection/recognition ONNX (Apache-2.0) from the pinned `rapidocr` 3.10.0 wheel, the extracted character dictionary and the ONNX Runtime Web 1.30.0 WASM runtime (MIT) with its license and third-party notices; `resources/offline-ai/ocr` carries the model license, RapidOCR's model notice and a NOTICE.
- Per-bundle manifests validate filenames, canonical paths, size and SHA. Source and build scripts stay in Git; weights/executables and private media stay ignored.

Preserve `THIRD_PARTY_NOTICES.md`, font/icon licenses, existing upstream notices and model licenses. Review all production/transitive dependency versions with an SBOM before a commercial release; the candidate research matrix is not a full npm/native/codec compliance certification. Deferred models must be separately reviewed before download/distribution; no gated model credentials or acceptance may be silently bypassed.

The existing offline preview is unsigned and has not passed a fresh-Windows-machine or old-CPU compatibility test. Both model runtimes are built for Windows x64 with AVX2, FMA, F16C, BMI2 and SSE4.2 enabled. Static linking removes non-system runtime DLL requirements from these two model executables; it does not certify the entire recorder on a clean machine. These are release gates, not proof that the current first integration cannot be tested locally.

The current package rules explicitly copy the application AGPL text and model/runtime license directories. Root audit Markdown documents and `THIRD_PARTY_NOTICES.md` are excluded from the application archive by the existing Markdown exclusion unless separately copied as resources. Before an external release, inspect the actual artifact for the required user-visible notices; this source inventory alone does not mean those documents are inside the installer.
